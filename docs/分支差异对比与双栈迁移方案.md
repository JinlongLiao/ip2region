# 分支差异对比与双栈迁移方案

后续实施结果见 [合并迁移与数据清洗验收记录](合并迁移与数据清洗验收记录.md)；以下保留初始对比和方案记录。

核对日期：2026-10-19。本文以本地 Git 提交和文件内容为证据，不代表远端实时状态。当前阶段仅输出对比与方案，不合并、不修改业务代码、不提交或推送。

## 1. 结论与目标

建议以 `old_version` 为承载分支，合入 `wlzn` 的代码演进，同时明确排除上游 IPv4 数据对自维护数据的替换。保留整个 `org.lionsoul.ip2region.merge` 自有维护工具包、资源和依赖；新增 IPv6 查询与制库能力。迁移分两步：先让新版解析器读取原有 IPv4 二进制，再验证新版制库器从自维护文本生成候选库。未经验证不替换现用库。

“不丢失”必须同时满足：自有源码保留、文本与旧库原件保留、IPv4 查询结果保持原有字段与内容、后续维护流程继续使用正确的数据入口。仅把旧文件放在目录中，而新版默认加载上游 IPv4 库，不算迁移成功。

## 3. 代码差异

| 范围 | old_version | wlzn | 迁移处理 |
| --- | --- | --- | --- |
| Java 查询器 | IPv4，`Searcher` 的创建与查询 API | 显式 `Version.IPv4/IPv6`，增加版本与字节地址工具 | 接入新版，检查下游编译兼容 |
| Java 高层查询服务 | 无对应 service 包 | `Config`、`ConfigBuilder`、`Ip2Region`、`SearcherPool` | 用独立 v4/v6 配置提供双栈查询；缓存及池数量按业务配置 |
| 内存缓存 | `byte[]` | `LongByteArray` 分片缓存 | 现有接收 byte[] 的调用不能机械照搬 |
| Java 制库 | `MakerTest` 主入口，IPv4 long 地址 | `MakerApp` 主入口，版本参数，IPv4/IPv6 字节地址 | 更新打包入口和使用命令，保留自有依赖 |
| Java 制库版本 | `1.0.0` | `3.1.0` | 代码及入口对齐 wlzn；最终自有制品版本发布时确定 |
| Java 查询版本 | 旧 API | POM 为 `3.3.7` | 本文版本仅指所核对提交，不宣称网络最新版本 |
| 自有维护工具 | merge 包内 16 个 Java 文件 | 自维护新增文件不在共同祖先中 | 全部保留，不能因上游入口更名而删掉 |
| 自有依赖 | fastjson2 `2.0.53`、nacos.common `${wlzn.version}`，wlzn.version=`1.3.4-SNAPSHOT` | maker POM 不含这些自有依赖 | 手工合并依赖，不整份使用上游 POM |
| Java 编译级别 | 自维护 maker 已改为 Java 8 | maker 为 Java 8 | 保持 Java 8，不退回共同祖先的 Java 6 |
| 其他语言 | 原有多语言绑定及 maker | C/C++、Go、Python、Rust 等大幅变化，新增其他绑定及测试 | 若全量合并则随上游保留；本次深度兼容评估集中于自有 Java 路径，其他语言不宣称已验证 |
| 忽略规则 | 包含 `.codegraph/` | 规则有独立演进 | 合并双方有效规则，保留索引目录忽略 |

自有数据链路：`IpLoopTest` 调用 `IpHelper` 获取候选 IPv4 归属结果，写入 `merget.txt`；`MergeTest` 读取基础文本及增补文本，按自有模型合并并覆盖第一个输入文件；制库器再由文本生成 xdb。`IpConveter` 与 `RegionItem` 使用 IPv4 数值和固定字段位置，不能直接用于 IPv6。

注意：`MergeTest` / `IpLoopTest` 虽以 Test 命名，却位于 main 源码并带实际写入或外部请求副作用，不是可随意运行的无副作用单元测试。`ReplaceTest` 有写死的 Windows 路径。迁移验证只对隔离副本执行维护工具，不自动请求外部 IP 服务、不覆盖真实数据。其历史算法正确性不因本次合并而自动获得保证。

## 4. 数据差异及实测

### 4.1 文件规模

| 分支 / 文件 | 字节数 | 文本行数 | 用途 |
| --- | ---: | ---: | --- |
| old_version `data/ip.merge.txt` | 43,199,905 | 719,901 | 自维护 IPv4 文本真源 |
| old_version `data/ip2region.xdb` | 11,913,980 | — | 自维护 IPv4 现有库，头部结构版本 2 |
| wlzn `data/ipv4_source.txt` | 36,682,346 | 516,858 | 上游 IPv4 文本 |
| wlzn `data/ip2region_v4.xdb` | 11,122,642 | — | 上游 IPv4 库，头部结构版本 3 |
| wlzn `data/ipv6_source.txt` | 77,031,212 | 670,732 | 上游 IPv6 文本 |
| wlzn `data/ip2region_v6.xdb` | 37,277,813 | — | 上游 IPv6 库，头部结构版本 3 |

两份 IPv4 文本均已逐行校验：地址合法，起止顺序正确，段间无重叠、无断档，从 `0.0.0.0` 覆盖至 `255.255.255.255`。三份文本每行均为 7 列。本轮未对 IPv6 全量校验连续性，不能将 IPv4 的结论延伸到 IPv6。

共同祖先 IPv4 文本为 683,844 行。按区间交集比较自维护文本与共同祖先，归属字符串不同的交集小段有 107,637 个，涉及 464,860,012 个 IPv4 地址。这是字符串差异统计，包含省市简称等变更，不等于新增准确地址数，也不是与 wlzn 新字段直接比较的结果。

### 4.2 最重要的兼容风险：同为 7 列，语义不同

| 位置（从 0 开始） | 自维护 IPv4 | wlzn IPv4 / IPv6 |
| --- | --- | --- |
| 0 | 起始 IP | 起始 IP |
| 1 | 结束 IP | 结束 IP |
| 2 | 国家 | 国家 |
| 3 | 原有 code，占位值常见为 0；不能直接认定为 ISO 国家代码 | 省 |
| 4 | 省 | 市 |
| 5 | 市 | ISP |
| 6 | ISP | 国家代码 |

自维护示例：`1.0.1.0|1.0.3.255|中国|0|福建|福州|电信`。

wlzn 示例：`1.0.1.0|1.0.3.255|中国|福建省|福州市|中国电信|CN`。

原有 `RegionItem(String)` 固定读取上述自维护列。直接让它读取 wlzn 数据会把省读成 code、市读成省、ISP 读成市。两边同时存在名称风格差异：例如福建/福建省、福州/福州市、电信/中国电信。IPv4 本次应原样保留，不顺带统一名称。

新版 maker 的 `Segment.iterate` 按前三段拆分，即起始 IP、结束 IP、其余 region 字符串；因此静态看允许保留自有 region 布局，但必须用完整制库和查询回归证实。`--field-list` 实现会排序字段索引，不能用它完成字段重排或补占位值。

### 4.3 合并冲突不能只看 Git 提示

上游相对共同祖先删除 `data/ip.merge.txt` 和 `data/ip2region.xdb`，新增 v4/v6 命名的数据。Git 启发式可能将大文件识别成重命名；这不代表业务上可替换。必须按明确文件清单处理，不能批量接受 ours/theirs。

重点人工检查：旧数据的修改/删除或重命名冲突、`maker/java/pom.xml`、`.gitignore`。自有 merge 包即使自动合并成功，也必须逐文件核对；新版 API 可能引发的是编译或行为冲突，Git 不会识别。

## 5. 建议迁移方案

### 阶段一：冻结和保护

1. 实施前重新核对分支、HEAD 和工作区；若存在新改动，重新生成差异基线。
2. 记录自有 21 文件清单及 SHA-256，保存完整旧源码、原始文本、旧 xdb 与现用制品。当前临时副本 `/tmp/ip2region-merge-preserve` 仅作本次辅助，不作为长期备份。
3. 在用户明确授权的隔离迁移分支或工作副本中实施；不直接改动 wlzn 分支，不自动提交推送。

### 阶段二：合入代码并保留自有维护流程

1. 全量合并 wlzn 代码时，先使用不自动提交的合并；逐项人工处理冲突。
2. 完整保留 `org.lionsoul.ip2region.merge` 包及 `src/main/resources/merget.txt`。
3. POM 采用新版 maker 入口 `org.lionsoul.ip2region.MakerApp`，合回自有依赖和 Java 8 配置；检查 shade 后自有工具仍可通过类路径调用。
4. 原路径 `data/ip.merge.txt` 与 `data/ip2region.xdb` 保持原件；保留上游 IPv6 文本与二进制。
5. 防止默认示例/脚本误用上游 IPv4 库：初期 v4 配置明确指向原有 `data/ip2region.xdb`。上游 IPv4 文件如保留，只能标注为参考，不能成为实际自维护数据入口。
6. 先不复制自维护文本到 `ipv4_source.txt` 形成第二份维护真源。若最终必须使用新版文件名，定义单向生成过程，生成文件不得人工独立编辑，且必须通过内容校验。

### 阶段三：验证旧库直读，再生成新版候选库

1. wlzn 的 `Searcher.verify` 明确识别结构版本 2 和 3，静态具备旧库支持路径；这不是“已验证所有旧库查询兼容”。用 `Version.IPv4` 指定旧库，分别验证文件、向量索引缓存和内存缓存查询。
2. 首轮优先保留旧库字节不变，避免同时升级代码和重新生成数据导致问题难以归因。
3. 用新版 maker 从 `data/ip.merge.txt` 生成独立候选输出，显式指定 `--version=ipv4`，默认保留全部 region 字段；不得将输出路径设为原库路径。
4. 对所有自维护区间边界及代表点比对旧库、新解析器读旧库、新生成库。发现差异先分辨原文本与旧库是否本来不一致，不能自动覆盖任一方。
5. 验证通过后才决定是否启用新版结构库。新版制库可能合并相邻相同 region，二进制哈希和物理段数不要求与旧库相同；地址到完整 region 的映射必须一致。

候选制库命令（仅供后续实施，本文未执行）：

```bash
cd maker/java
mvn test package
java -jar target/ip2region-maker-3.1.0.jar --src=../../data/ip.merge.txt --dst=../../data/ip2region_v4.candidate.xdb --version=ipv4
```

必须检查实际 jar 文件名、运行输出及产物有效性，不能仅依赖进程退出码：当前上游 `MakerApp.main` 捕获异常后打印信息，未保证失败时非零退出。

### 阶段四：双栈查询与业务字段契约

使用 `Ip2Region.create(v4Config, v6Config)`，两个配置分别绑定旧自维护 IPv4 库和上游 IPv6 库。生命周期由业务服务管理，停服时关闭；不要在每次请求中重复初始化或关闭。

IPv4 返回维持 `国家|code|省|市|ISP`，确保旧消费方兼容。IPv6 原生返回为 `国家|省|市|ISP|国家代码`。实施前必须确认业务是否统一输出旧布局：

- 若统一，建议在业务适配层显式转换 IPv6 为 `国家|0|省|市|ISP`；国家代码另行保留，不能偷偷塞入原 code 字段。`0` 是待确认的占位策略。
- 若保留各自原生返回，消费方必须按 IP 版本分别解释，并有对应测试，不能共用旧数组下标。

这项业务契约尚未确定，方案不代替用户作出最终取舍。IPv4 自有维护工具继续仅处理 IPv4；本次不额外扩展其采集、补丁和区间合并算法到 IPv6。

## 6. 验证与放行条件

| 验证项 | 方法 | 放行条件 |
| --- | --- | --- |
| 自有源码与资源 | 与冻结清单逐文件核对哈希；必要适配单独 review | 不漏文件、不丢依赖，修改原因可追溯 |
| 原始数据保护 | 旧文本、旧库 SHA-256 | 原件哈希保持一致 |
| 文本与旧库一致性 | 对旧文本每段首尾和中间点查询旧库；必要时解析双方索引区间比较 | 先识别迁移前已有不一致 |
| IPv4 新旧解析行为 | 所有源段边界、随机点、保留地址及自维护差异范围 | 完整 region 字符串一致 |
| 新版候选库 | 全量地址区间映射比较，辅以新旧查询器边界测试 | 无地址覆盖或 region 语义差异 |
| IPv6 | 文本合法性与范围、边界、压缩写法、无命中与非法输入 | 与选定数据及业务返回契约一致 |
| 缓存策略 | NoCache、VIndexCache、BufferCache | 三种结果一致；资源可关闭 |
| 并发与关闭 | service 池借还、异常归还、并发查询和关闭 | 无串结果、泄漏、死锁；明确容量与关闭边界 |
| 维护链路 | 在隔离数据副本运行补丁合并与制库 | 原命令用途保留，输出可验证，不覆盖真源 |
| 下游兼容 | 查找实际消费方、构建和回归 | API、字段下标及打包资源路径均通过 |
| 构建与格式 | 两个 Java 模块测试与打包、项目格式检查、git diff --check | 受影响验证通过，未通过项明确记录 |

本机 Maven 仓库从 `~/.m2/settings.xml` 的 localRepository 读取，当前解析为 `${user.home}/Applications/file/cache/maven`；后续构建沿用配置，不通过 `-Dmaven.repo.local` 覆盖。构建依赖缺失与业务失败分别记录。

原文本覆盖检查不能证明现有 xdb 与文本逐项一致，也不能证明新版解析正确。本轮没有运行编译、单元测试、制库或性能测试，没有扫描仓库外实际业务消费方。

## 7. 回退与待确认项

回退同时恢复旧应用制品、旧配置、旧 xdb，避免仅回退代码而继续使用新版结构库。上线前演练，不覆盖原始库；部署及生产验收另行授权。Git 回退、分支创建、提交和推送均按用户授权执行。

实施前需确定：

1. IPv6 对外返回使用原生布局还是统一为原有五字段布局；若统一，原 code 占位与国家代码如何处理。
2. 实际消费服务及调用方式，以判断是否需要旧 Searcher API 兼容适配；当前仓库证据不足，不能默认不需要。
3. 是否接受先保留结构版本 2 的旧库，仅升级解析代码，再在第二阶段切换重新生成的库。

本方案默认完全保留自维护 IPv4 数据，不混入上游新版 IPv4 数据。若后续希望同时吸收上游 IPv4 内容，应另行设计基于共同祖先、字段归一和自维护覆盖优先级的区间级三方数据合并，不能以 Git 文本冲突解决代替。
